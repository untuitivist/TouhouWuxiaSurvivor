# Windows 诊断构建与日志回传

本指南用于定位“另一台机器帧率异常、卡顿或导出后崩溃”等无法在开发机复现的问题。
诊断构建是当前游戏版本的一个构建变体，不是新的语义版本，也不能替代正式发行包的性能结论。

## 构建诊断包

在项目根目录运行：

```bat
tools\diagnostics\build_diagnostics.cmd
```

脚本读取 `project.godot` 的唯一版本，使用 `Windows Diagnostics` 预设导出 Release 优化代码，
并把控制台包装器、两种渲染后端启动器和本指南放入 `release\diagnostics`。PCK 继续内嵌，
诊断特性只在该预设启用。若目录已经存在，脚本会拒绝覆盖；先人工确认并移动旧目录，不要让
脚本静默删除上一轮证据。

诊断目录中至少应包含：

- `TouhouWuxiaSurvivor_<version>_windows-x86_64-debug.exe`
- 同名 `.console.exe`
- `Run_Diagnostics_D3D12.cmd`
- `Run_Diagnostics_OpenGL.cmd`
- `run_diagnostics_core.cmd`
- `README_diagnostics.md`

分发时发送整个目录，不能只发送主 EXE；控制台包装器和启动脚本是日志闭环的一部分。

## 复现步骤

1. 先运行 `Run_Diagnostics_D3D12.cmd`，按正常操作进入同一局并复现至少 60 秒。
2. 正常退出游戏；启动器会打开本次唯一的 `logs\session_d3d12_*` 目录。
3. 再运行 `Run_Diagnostics_OpenGL.cmd`，使用相同分辨率、内容包、角色、路线和复现时长。
4. 正常退出，并保留新的 `logs\session_opengl_*` 目录。
5. 将两个完整会话目录一并回传，不要只截 F3 或只发送 `godot.log`。

每次启动都会创建新目录，不覆盖旧会话。引擎日志、会话元数据和结构化性能采样必须落在同一
目录，避免第一次启动修复旧设置后丢失原始证据。强制结束进程可能丢失最后几秒数据；能正常
退出时优先正常退出。

## 日志回答什么问题

诊断会记录以下只读信息：

- 游戏版本、构建变体、命令行、Windows 版本和处理器架构。
- 实际渲染后端、显卡适配器、窗口/屏幕尺寸、VSync 和运行时帧率上限。
- FPS、平均/最大帧间隔、Process/Physics 时间以及视口 Render CPU/GPU 时间。
- Draw Calls、渲染对象/图元、显存、纹理、缓冲区、节点和资源数量。
- 托管堆、GC 次数、进程内存和 CPU 使用率。
- 敌人池、存活敌人、Boss、双方弹丸、掉落物、灵息和碰撞候选数量。
- 活跃/待生成区块、等级、启用内容、角色、暂停状态、当前模态层和素材回退数量。

采样按约一秒聚合并批量写盘，不逐帧打印。诊断器自身发生异常时会停用采样和视口计时，
不得因日志失败持续拖慢游戏或改变游戏退出码。

## 判读顺序

1. **菜单已经很慢**：先查实际 `Engine.MaxFps`、VSync、分辨率、适配器和渲染后端；此时 ECS
   战斗实体还不存在，不能先归因于敌人或弹幕。
2. **D3D12 慢而 OpenGL 正常**：优先调查驱动、适配器选择和 D3D12 路径，不先修改玩法预算。
3. **进入世界首秒尖峰**：对照区块生成、资源首次加载和 Pipeline Compilation；它与持续低帧
   是两类问题。
4. **随敌群或弹幕持续恶化**：比较碰撞候选、双方弹丸、Draw Calls、Rendered Objects 和
   Render CPU/GPU。
5. **周期性顿挫**：比较 GC、暂停/模态状态、帧时间峰值和区块流送数量。
6. **只在地图操作时卡顿**：检查地图纹理重建尺寸和次数，不把它归入战斗 ECS。

“无上限”只表示不设置软件 FPS 上限，不保证显示器刷新、VSync、驱动调度和帧时间天然稳定。
判断卡顿时优先看帧时间分布和运动连续性，不只看某一秒的 FPS 数字。

## 回传内容与隐私

会话包含硬件、系统、渲染器、游戏设置、运行参数和性能数据，可能包含本机目录路径。
回传前可以查看文本内容并移除不希望分享的个人路径，但不要删除时间戳、版本、后端、适配器、
设置和性能采样。诊断包继续遵守内部原作素材边界，不代表获得公开再分发许可。

正式发行使用 `build_release.cmd`；只有用户明确要求诊断构建时才运行本指南的脚本。
